# 05 · LeadGen query timings (CP4)

Generated by `dbms/run_query_timings.py` from the `Execution Time` lines in `dbms/plans/` (no number is typed by hand).

## How it was measured

- Database: `dbms/03_schema.sql` + `dbms/seed_test_data.sql` (synthetic test data, fixed seed) on PostgreSQL 16.15 (Ubuntu 16.15-0ubuntu0.24.04.1), Linux x86_64.
- Row counts: evidence 60000, lead_score_components 50000, signal_evidence 45000, candidate_signals 45000, candidates 30000, businesses 20000, business_contacts 20000, business_source_records 20000, llm_assessments 12514, leads 10000, lead_review_events 6666, campaigns 80, workspace_members 47, clients 40, users 40, scoring_model_weights 29, workspace_services 20, workspaces 8, scoring_models 6, signal_types 6, score_dimensions 5, service_playbooks 3.
- Every query is `PREPARE`d once and run **3 times** with `EXPLAIN (ANALYZE, BUFFERS) EXECUTE`. Average = mean of the 3 `Execution Time` values. All 3 plans are in `dbms/plans/<ID>.txt`.
- WRITE queries run inside `BEGIN … ROLLBACK`, so they really execute (constraints, FK checks, index updates are timed) but leave the data unchanged for the next run.
- Parameters are real ids from the test data (the busiest campaign of `Agency 1`, one of its reviewed leads, …); each plan file lists the values used.
- Run as the table owner, so Supabase row-level-security policies are not part of the timing.

## Query analysis

- **Slowest reads:** R7 (20.903 ms), R13 (9.690 ms), R23 (6.954 ms), R19 (2.110 ms). **Slowest writes:** W24 (52.623 ms), W7 (0.562 ms), W5 (0.466 ms). Every other query averages under 1.9 ms.
- **Run 1 is slower than runs 2-3** for most queries: the first EXECUTE also builds the plan and reads pages from disk into shared buffers (`shared read` in the plan); later runs find them cached (`shared hit`). That is why the average of 3 runs is reported.
- **Seq Scan on small tables is correct, not a problem.** users (40 rows), workspaces, workspace_members, service_playbooks, clients, campaigns (80), scoring_models, score_dimensions and signal_types fit in one or two 8 KB pages, so reading the whole table is cheaper than walking an index first (R1-R6, R8, R9, R18, W4, W8, W17).
- **Lookups by key use the PK / UNIQUE indexes from 03_schema.sql:** R10 (business_source_records_pkey), R11 (businesses_normalized_domain_key, the discovery dedup), R14 (uq_evidence_business_url_time), R15 and R16 (uq_evidence_id_business, candidate_signals_pkey), R17 (uq_llm_assessments_candidate_time gives the latest assessment without a sort), R20/R21/W21 (leads_pkey + lead_score_components_pkey), W22/W23 (PK). Composite UNIQUE constraints whose first column is the filter column (candidates (campaign_id, business_id), evidence (business_id, ...)) double as the index for that column, so R12, R13, R19 and R24 find one campaign's candidates with a Bitmap Index Scan.
- **R7 (campaign list) and R23 (dashboard)** count candidates and leads for *every* campaign of a workspace. One workspace owns about 1/8 of all candidates and leads, so the planner correctly hashes whole tables (Seq Scan + Hash Join + aggregate) instead of thousands of index probes. If this grows, the fix is cached counters per campaign (updated by the scoring job), not an index.
- **R13 / R19 / R24** join one campaign's candidates to businesses; R13 hashes businesses (Seq Scan on 20,000 rows) because it lists all 375 candidates with a signal count, R19 and R24 probe businesses_pkey for the few leads they return.
- **Missing index found: lead_review_events(candidate_id).** R22 (review history) does a Seq Scan of lead_review_events, and W24 (delete a draft campaign) spends most of its time in the trigger `lead_review_events_candidate_id_fkey` (see `plans/W24.txt`): for every cascaded lead it has to search lead_review_events by candidate_id, and no index starts with that column. PostgreSQL indexes the referenced side of a FK (the PK) automatically, but never the referencing column. Recommended for 03_schema.sql: `CREATE INDEX idx_lead_review_events_candidate ON leadgen.lead_review_events (candidate_id, acted_at);` (candidate first for the equality, acted_at for R22's ORDER BY). The same rule suggests indexes on other FK columns that are searched or cascaded, e.g. `campaigns (workspace_id)` and `leads (review_status)` once data grows.
- **Writes:** single-row inserts and updates (W1-W23) stay well under a few ms; their cost is the FK checks and UNIQUE index updates the schema requires. ON CONFLICT upserts (W1, W3, W9, W10, W11, W14, W20) use the same UNIQUE index that guarantees the rule, so idempotent retries of background jobs cost no extra lookup.
